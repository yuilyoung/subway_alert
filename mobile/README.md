# Android 앱 (데모)

Android 7.0 이상을 목표로 한 Expo/React Native 프로토타입입니다. Android 개발 도구가 설치된 환경에서 `npm ci` 후 `npx expo run:android`로 개발 빌드를 만듭니다. 위치 백그라운드 작업은 네이티브 권한·서비스 설정이 포함된 개발 빌드에서 확인해야 하며, Expo Go만으로 실기기 기능을 보장할 수 없습니다. 자바스크립트 단위 테스트는 `npm test`, Android JS 번들 검사는 `npx expo export --platform android`입니다.

앱에서 데모 역을 선택해 경로를 시작하거나 최대 5개 즐겨찾기를 저장합니다. 즐겨찾기별 요일과 시간대를 설정한 뒤 앱을 열어 출퇴근 감지 알림을 켜면 위치 포그라운드 서비스가 작동하며, 출발역 부근에 있을 때 확인 알림을 표시합니다. 기본은 월~금 07:00–09:00이며 기존 항목의 요일·시간도 수정할 수 있습니다. 야간 조건은 시작 요일 기준이고 종료 시각은 포함하지 않습니다. 실제 탑승 여부를 확정할 수 없으므로 경로 감시는 **사용자가 앱에서 직접 시작**해야 합니다. 수동 경로는 GPS가 신선하고 정확하며 이전 역 외부에서 근처로 들어온 경우에만 데모 하차 알림을 표시합니다. 한 정거장 경로는 즉시 데모 안내 후 종료합니다. 사용자가 알림·위치·백그라운드 위치 권한을 허용해야 합니다.

**실제 하차용이 아닙니다.** 포함된 2호선 5개 역 좌표는 검증되지 않은 대략값입니다. 지하 위치 손실, Android 절전·강제종료·재부팅 등으로 알림이 지연되거나 누락될 수 있습니다. 데모 하차 감시는 실제 열차나 역 방향을 확인하지 못하며 서버 열차 조회 또는 FCM과 연결되어 있지 않습니다. 역 시설도 실제 데이터가 없습니다. 새로운 역 직접 추가, 정확한 전국 역 검색, 환승 경로, 알림용 탑승 열차 확정·추적, 진짜 완전 자동 시작 및 실제 역 시설 정보는 미구현입니다.

백그라운드 작업은 사용자 설정을 직접 수정하지 않고 경로 ID별 별도 진행상태를 기록해 취소된 경로를 복원하지 않도록 합니다. 그러나 기기 환경에서 알림 발송과 취소/새 경로 시작이 동시에 발생할 때의 경쟁, OS에 의한 서비스 종료, 권한 회수, 알림 채널 및 위치 정확도는 실기기 테스트가 필요합니다. 화면에 표시되는 진행상태는 앱 복귀 시 새로고침됩니다.

출퇴근 제안은 즐겨찾기별 시간대의 시작 날짜로 중복을 억제합니다. 같은 야간 시간대에 자정을 넘어도 한 번만 요청하며, 이미 제안한 항목이 다음 적격 즐겨찾기를 막지 않습니다. 알림 직전에 최신 조건·자동 감지·진행 경로를 다시 확인합니다. 완료된 경로의 별도 진행 기록은 다음 출퇴근 제안을 막지 않습니다. 저장 실패에는 알림을 요청하지 않고, 알림 요청 실패 뒤에는 같은 시간대에 자동 재시도하지 않습니다. [자세한 사용법과 한계](../docs/commute-schedules.md)를 확인하세요.

## 열차 정보 조회 (시험 기능)

앱의 서버 연결 화면에서 HTTPS origin(예: 호스트와 포트만 포함한 주소)과 운영자가 별도 전달한 기기 API 키를 입력하고 저장합니다. 키는 32~128자의 base64url 문자이며 없거나 형식이 잘못되면 요청을 보내지 않습니다. 연결 정보는 SecureStore에 저장합니다. origin을 변경하면 입력 키를 비우고 이전 연결의 응답을 무효화하므로 새 주소에 맞는 키를 다시 저장해야 합니다. 서울 API 키나 서버 서비스 계정 키를 이 입력란에 넣지 않습니다. 참가자용 키도 APK 공용 비밀로 내장하지 않습니다.

보호 요청은 `expo/fetch`로 `Authorization: Bearer <key>`를 전송하며 redirect는 거부합니다. 서버의 401은 키 확인, 503은 서버 키 설정 확인, 429는 `Retry-After`에 따른 대기를 안내합니다. 정확히 `GET /api/health` 외 모든 경로에 인증이 필요하며 localhost에도 같은 규칙이 적용됩니다. 이 키는 소수 신뢰한 시험 참가자 접근용이고 일반 사용자 로그인이나 FCM 기기 소유 증명이 아닙니다.

화면의 2호선 열차 조회에는 별도 Spring 서버가 필요합니다. 샘플 모드는 서울시 공개 `sample` 응답 최대 5건만 반환하며 탑승 열차 판별 및 하차 알림에 이용할 수 없습니다. 실시간 연동은 서버의 HTTPS 및 API 키 설정과 실제 환경 검증이 필요합니다. 선택한 공개 샘플 열차로 아래 TEST 감시를 등록할 수 있습니다. 실제 하차 알림과는 연결되지 않습니다. 화면의 정보 시각은 서버가 서울시 시각을 서울 시간대로 해석한 값이며 실측이 필요합니다.

Metro 개발 모드(`__DEV__`가 true)에서는 에뮬레이터에서 PC 서버에 `http://10.0.2.2:8080`을, USB 연결 기기에서는 `adb reverse tcp:8080 tcp:8080` 이후 `http://127.0.0.1:8080`을 사용할 수 있습니다. Expo가 생성한 Android debug manifest는 디버깅을 위해 cleartext를 허용하지만 앱은 해당 두 주소와 localhost만 허용합니다. 독립 설치용 번들은 debug APK라도 `__DEV__`가 false일 수 있어 HTTP를 허용하지 않습니다. 일반 RN debug 빌드는 Metro 개발 서버 연결을 요구할 수 있습니다. 릴리스 및 독립 번들은 검증된 TLS와 유효한 인증서를 사용하는 HTTPS 서버가 필요합니다. 앱에 서울 API 키를 입력하거나 저장하지 않습니다. 이 구성은 Android 실기기에서 아직 검증되지 않았습니다.

## FCM 시험 감시 (실제 하차 알림 아님)

열차 조회에서 **공개 샘플** 열차를 선택한 뒤 사용자가 목적지 직전역과 목적지를 직접 입력합니다. 앱은 Android 알림 채널 `subway-alerts`와 권한을 설정하고 `getDevicePushTokenAsync()`로 **네이티브 FCM 등록 토큰**을 얻어 서버의 TEST 세션에 등록합니다. 앱과 서버는 테스트 전용 알림만 처리하며 사용자 입력은 실제 경로 검증이 아닙니다. 서울 샘플은 5건으로 전체 운행이 아닙니다. 서버의 `FCM_ACCEPTED`는 FCM 서버가 요청을 수락한 상태이지 기기에 알림이 도착했다는 뜻이 아닙니다.

1. Firebase 프로젝트에서 Android 패키지 `com.yuilyoung.subwayalert`를 등록하고 `google-services.json`을 받습니다. 이것은 **서버 서비스 계정 비밀 키와 다른 파일**입니다. 기존 APK를 수정하는 방식으로는 적용되지 않습니다.
2. 저장소 바깥에 이 파일을 보관하고 빌드 환경의 `GOOGLE_SERVICES_JSON` 환경변수에 그 파일의 절대 경로를 지정해 Expo Android 네이티브 프로젝트를 생성하고 앱을 다시 빌드합니다. 앱 설정은 이 변수가 있을 때만 `android.googleServicesFile`을 추가합니다. 이전에 만든 Android 프로젝트에는 설정이 자동으로 소급 적용되지 않을 수 있으므로, 기존 네이티브 수정사항을 보존한 뒤 생성 과정을 다시 실행하세요.
3. 서버의 Firebase 구성과 신뢰할 수 있는 HTTPS 연결을 준비합니다. 서버 서비스 계정 비밀 키는 앱·저장소에 넣지 않습니다. 실제 FCM 토큰은 대화창이나 로그에 복사하지 마세요.
4. Android 알림 권한을 허용하고 샘플 열차·목적지 정보를 선택해 시험 감시를 시작한 뒤 `시험 알림 보내기`로 확인합니다. 토큰 발급 실패나 FCM 미설정은 성공처럼 표시하지 않습니다. 서버 수락 후에도 실제 기기 도착·시간은 따로 확인해야 합니다.

시험 등록은 origin·API 키·클라이언트 UUID·256비트 세션 비밀·원래 요청을 SecureStore에 PENDING으로 먼저 저장합니다. PENDING에는 같은 요청 재시도를 위해 원래 FCM 토큰이 포함됩니다. 저장 실패 시 POST를 보내지 않고 응답 유실·최종 저장 실패 시 기록을 유지합니다. 새 등록 대신 결과 조회·동일 요청 재시도·종료를 사용하며, 원래 열차 관측이 60초를 넘으면 POST 재시도는 막고 조회·종료만 허용합니다. ACTIVE로 확인되면 재시도용 요청과 FCM 토큰은 저장 기록에서 제거합니다.

복원된 PENDING/ACTIVE 기록은 POST를 자동 전송하지 않습니다. 기존 정책대로 기기 FCM 토큰을 확인할 수 없으면 종료를 시도하며, 종료 확인 전까지 비밀을 보존합니다. 다른 origin에 기존 비밀을 보내지 않고 같은 origin의 새 API 키를 사용할 수 있습니다. 읽히지 않거나 손상된 기록을 빈 상태로 취급해 새 감시를 만들지 않습니다. 세부 동작은 [등록 응답 유실과 복구](../docs/registration-recovery.md)에 있습니다. 실제 네이티브 저장·프로세스 종료·재부팅·FCM 수신·실제 하차 알림은 아직 기기 검증이 필요합니다.

호출 예산은 프로세스 전체 600회/분, 키별 60회/분, 세션 생성 키별 3회/분입니다. 직접 열차 조회는 모든 키가 6회/분·서울 날짜 하루 240회를 공유합니다. 시험 감시 폴링은 별도 하루 600회로 sample 모드에서 합계 최대 840회/일/프로세스입니다. 앱을 다시 설치하거나 다른 기기를 쓰더라도 서버 키별·전체 예산을 늘려 주지 않으며 서버 재시작·복제 시 예산은 초기화·증가합니다. 운영 과금 제어는 아닙니다.

직접 조회 240회는 클라이언트 요청의 허용 횟수입니다. 실키 LIVE 조회 한 번은 최대 5페이지의 서울 API 호출을 수행할 수 있어 외부 호출 840회 상한은 sample 모드에만 해당합니다. 실키의 통합 외부 호출 예산은 후속 구현이 필요합니다.
