# 즐겨찾기 출퇴근 조건 편집

현재 앱은 즐겨찾기를 평일로만 만들고 저장된 시간·요일을 수정할 수 없다. 이번 작업은 요일 선택, 시간 수정, 야간 조건과 알림 중복 억제를 완성한다. 이전 PR #6은 열어 두고 그 head 96d5147에서 별도 브랜치로 개발한다. main 병합·클라우드 설정 변경은 수행하지 않는다.

## 선택과 범위

역 목록을 확대하는 방법도 검토했지만 현재 경로 계산이 5개 역의 단일 배열 순서에 의존하므로 순환선·지선 정보를 검증하기 전에는 잘못된 경로를 만들 수 있다. 외부 계정·추가 데이터 없이 현재 앱에서 사용할 수 있는 출퇴근 조건 편집을 우선한다. 이는 구현자의 선택이며 사용자가 역 확대를 취소했다고 해석하지 않는다.

- 즐겨찾기 최대 5개, 출발·도착 중복 금지, 기존 역 ID·즐겨찾기 ID와 사용 여부를 보존한다. 5개가 차도 기존 조건 수정은 가능하다. 삭제된 ID의 수정은 새 등록으로 바꾸지 않는다.
- 월~일 중 하나 이상 선택하고 HH:MM 24시간 형식·서로 다른 시작/종료 시각을 검증한다. 기본은 기존 월~금 07:00–09:00이다. 기존 저장 기록은 그대로 읽는다.
- 시간대는 기기 현지 시간이다. 시작 포함·종료 제외이며, 23:00–01:00 같은 야간 조건은 시작 요일에 속한다. 일요일 밤부터 월요일 새벽도 일요일 조건이다.
- UI에 실제 선택 요일·시간, 수정·취소·저장 상태를 표시한다. 저장 전 초안은 기존 자동 감지에 반영하지 않는다. 감시 시작·위치 권한·탑승 확인 흐름은 기존 데모 정책을 유지한다.
- 백그라운드 제안은 즐겨찾기별로 해당 시간대 시작 날짜 + 시작/종료 시각의 occurrence key를 사용한다. 같은 야간 시간대의 자정 전후에 두 번 제안하지 않는다. 이미 제안한 항목은 건너뛰고 다음 적격 항목을 확인한다. 같은 저장 키의 버전1 이력에 현재·전일의 시작 날짜와 미래 기록을 보수적으로 보존해 A→B→A 편집에서도 소비한 A를 잊지 않는다. 전일보다 오래된 과거 기록은 정리하며 최대128개를 넘기기 전에 해당 즐겨찾기의 새 제안을 보류한다. 살아 있는 기록을 버려 공간을 만들지 않고 손상 이력을 덮어쓰지 않는다. 다른 적격 즐겨찾기는 계속 확인한다.
- 제안 직전 자동 감지 여부, 진행 중 경로 없음, 즐겨찾기 존재·사용 여부·경로·조건, 현재 시간대·위치 신선도를 다시 확인한다. 편집·삭제·중지 후 오래된 조건으로 알리지 않는다. 완료 진행 기록을 읽은 뒤에는 설정을 다시 읽어 그 I/O 도중의 중지·새 경로·조건 수정도 반영한다. 완료한 같은 경로 ID만 종료 상태로 해석한다. 한 위치 이벤트에 최대 한 제안이다.
- 한 JS 실행 환경에서 제안 처리를 직렬화한다. 마커를 알림 요청 전에 저장하므로 저장 실패 시 알리지 않고 알림 요청 실패 후 같은 시간대 자동 재시도는 하지 않는다. 여러 OS 프로세스에 걸친 exactly-once는 보장하지 않는다. 기존 날짜만 담은 일별 마커도 해당 날짜/야간 시작 날짜에는 억제 기록으로 인정한다.
- 역 데이터는 기존 5역·대략 좌표 데모이며 실제 하차 판단, 시설, FCM·Supabase·Tunnel·Play 연동을 활성화하지 않는다.

## 검증과 경계

요일 선택·빈/손상 조건 거부, 시작/종료 경계, 일→월 야간, 5개에서 수정·ID/사용 여부 보존·다른 항목 보존·중복/삭제 ID 거부를 단위 검사한다. 실제 제안 처리 함수에 메모리 저장소·가짜 시계·알림 전송 경계만 주입해 자정 중복, 앞 항목 소비 후 다음 후보, 동시 호출, 비동기 처리 중 수정/삭제/중지/시간 경과, 저장 실패와 알림 실패를 검증한다. 전체 Node·Python 테스트와 Android export 및 CI를 실행한다. Node/번들은 Android 실기기 UI·백그라운드 수신 검증과 구분한다.
