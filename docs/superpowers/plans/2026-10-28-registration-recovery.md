# 등록 복구 구현 계획

Spec: `docs/superpowers/specs/2026-10-28-registration-recovery-design.md`

1. 서버: 필수 헤더·동일 요청 재생·본문/비밀 충돌·동시 등록·취소 선행 표식·만료/용량 테스트를 먼저 실패시킨 뒤 서비스와 컨트롤러를 구현한다. 기존 테스트를 새 HTTP 계약으로 갱신하고 Maven 전체 검사를 통과한다.
2. 앱: Crypto ID/비밀 생성, PENDING 선저장, 응답 유실 후 동일 요청 재시도, 오래된 POST 차단, 재시작 복원과 취소 실패 보존, origin 변경과 저장 실패 테스트를 먼저 실패시킨 뒤 API·저장 흐름·화면을 연결한다. Node 전체 검사와 Android JS 번들을 검증한다.
3. 통합: API 문서·설계와 검증 기록을 갱신하고 독립 리뷰를 수행한다. 메모리/보관 범위와 외부 기기 검증을 구분한다. 별도 PR로 올려 서버·앱·Docker·APK CI 결과를 확인하며 자동 병합하지 않는다.

공유 계약은 Idempotency-Key UUID v4 = 세션 ID, X-Session-Token 64자 소문자 hex, 기존 7개 TEST 본문, POST 응답 구조 유지, 400/409/503 구분, 기존 GET/DELETE 재사용이다. 앱 저장 스키마는 PENDING/ACTIVE와 이전 ACTIVE 호환을 명시한다.

리뷰 중점: 응답 유실 뒤 비밀 미보관, 요청 본문과 토큰 변동, 재생 시 만료/상태 초기화, 취소-생성 경쟁, 500개 메모리 용량, 앱 저장 실패·복원 오류가 새 등록으로 이어지는 경로, 오래된 요청의 재생성과 다른 origin 비밀 전송.
