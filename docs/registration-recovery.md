# 감시 등록 응답 유실과 복구

개정일: 2026-10-28. TEST 감시 등록의 재시도와 앱 기록 복구를 다룹니다. Firebase 실기기 수신이나 실제 하차 알림 검증은 별도입니다.

## 앱 동작

앱은 Firebase 기기 토큰을 얻은 뒤 암호학적 난수로 UUID와 256비트 세션 비밀을 만듭니다. origin·API 접근 키·세션 ID·비밀·원래 요청을 한 SecureStore 항목에 PENDING으로 저장한 후에만 등록 POST를 보냅니다. 서버 응답의 ID·비밀·상태·만료시각을 확인하고 ACTIVE로 저장합니다.

| 상황 | 동작 |
| --- | --- |
| 처음 저장 실패 | 등록 요청을 보내지 않음 |
| POST 응답 유실·잘못된 응답·최종 저장 실패 | PENDING 기록 유지, 새 등록 차단 |
| 등록 결과 확인 | 이미 아는 세션 ID·비밀로 GET 조회 |
| 동일 요청 재시도 | 같은 ID·비밀·본문 사용, 새 난수·기기 토큰 생성 안 함 |
| 원래 관측이 60초를 넘음 | 새 생성이 될 수 있는 POST 재시도 차단, 조회·종료 가능 |
| 앱 재시작 | 기존 기록 복원, POST 자동 전송 안 함. 기기 토큰을 확인할 수 없으면 기존 정책대로 취소 시도 |
| 취소 실패 | 기록과 비밀 보존, 연결을 확인한 뒤 조회·종료 재시도 |

서버 주소를 바꿔도 등록한 origin으로만 요청합니다. 같은 origin에서 API 접근 키를 교체할 수 있지만 기존 세션 비밀은 그대로 필요합니다. 보관 기록이 손상되거나 읽히지 않으면 새 등록을 진행하지 않습니다. 기본 포트 표기 차이는 같은 origin으로 정규화합니다.

## HTTP 계약

`POST /api/monitor-sessions`에는 다음 헤더가 필수입니다. 비밀을 URL이나 로그에 넣지 않습니다.

| 헤더 | 값 |
| --- | --- |
| Authorization | Bearer + 운영자가 제공한 기기 API 접근 키 |
| Idempotency-Key | 앱이 만든 정규 소문자 UUID v4, 생성할 세션 ID와 같음 |
| X-Session-Token | 앱이 만든 32바이트 난수의 소문자 hex 64자 |

본문은 기존 lineId·trainId·direction·previousStation·destinationStation·fcmToken·mode의 7개 TEST 필드를 사용합니다. 열차번호의 앞자리 0은 유지합니다. 서버는 세션 비밀과 정규화한 요청의 해시를 보관하고, 재생을 위해 원문 세션 비밀이나 응답을 캐시하지 않습니다.

같은 ID·비밀·본문의 재전송은 원래 세션의 현재 상태와 원래 만료시각을 반환합니다. 재전송으로 만료시각을 연장하거나 취소·만료된 감시를 다시 시작하지 않습니다. 이 확인은 알림 전송을 수행하지 않습니다.

| 응답 | 의미 |
| --- | --- |
| 200 | 처음 생성 또는 동일 요청의 현재 결과 반환 |
| 400 | 필수 헤더·UUID·세션 비밀·TEST 본문 형식 오류 |
| 409 | 같은 ID에 다른 세션 비밀이나 본문 사용 |
| 401 / 429 | API 접근 키 오류 / 요청 한도, 재시도에도 기존 제한 적용 |
| 503 | 새 항목 용량 부족, API 키 미설정 또는 감시 저장소 장애 |

조회·종료는 기존 `GET/DELETE /api/monitor-sessions/{id}`와 같은 API 키·세션 비밀을 사용합니다. 최초 등록 응답을 잃어도 앱이 이미 ID와 비밀을 알고 있습니다. 이전 APK에는 새 필수 등록 헤더가 없으므로 이번 변경이 포함된 앱을 빌드해야 합니다. 기존 ACTIVE 저장 기록은 읽을 수 있습니다.

## 취소가 먼저 도착했을 때

유효한 새 ID·클라이언트 세션 비밀로 DELETE가 등록보다 먼저 도착하면 서버는 CANCELLED 표식을 보관합니다. 뒤늦은 같은 등록은 CANCELLED를 반환하며 감시를 시작하지 않습니다. 다른 비밀은 기존 세션 정보를 얻거나 덮어쓸 수 없습니다. 조회는 알 수 없는 ID를 새로 만들지 않습니다.

취소 표식도 최대 500개 항목에 포함됩니다. 한도가 찬 경우 새 생성·새 취소 표식은 503이지만 기존 세션 취소와 동일 요청 재생은 계속 가능합니다. 앱은 취소 확인 전에 기록을 지우지 않습니다.

## 한계와 검증

기본 메모리 모드는 서버 재시작 시 세션·표식이 사라집니다. 선택형 PostgreSQL 모드는 원래 ID·만료·취소 표식을 복원하되 진행 중 감시는 종료하고 자동 전송하지 않습니다. 두 모드 모두 2시간 만료와 추가 1시간 보관 후 기록을 정리합니다. PostgreSQL은 같은 DB의 백엔드 하나만 허용하며 여러 인스턴스의 exactly-once를 제공하지 않습니다. [DB 저장과 재시작](durable-receipts.md)에 설정과 장애 정책을 설명합니다. 앱은 오래된 등록을 자동 생성하지 않습니다. 취소 전에 발송이 시작된 FCM을 회수할 수 있다는 뜻도 아닙니다.

로컬 검증: 서버 Maven verify 68개(실패·오류·건너뜀 0), 모바일 Node 54개, Python 27개가 통과했습니다. Expo SDK54용 Crypto ~15.0.9를 포함한 Android JS 번들(746모듈)을 생성했습니다. 패키징한 JAR에서도 취소 선행·응답 본문 미수신·기존 ID 조회·동일 요청 재생·409 충돌을 확인했습니다. 이 smoke 검사는 취소된 의도만 사용해 활성 감시·서울 API/FCM 요청을 만들지 않습니다. 원격 CI와 새 APK 결과는 PR에서 별도로 확인합니다. 기본 범위는 서버의 실제 서비스·HTTP 필터·동시 등록·취소 선행, 앱의 전송 경계에서 응답 유실·선저장 실패·복원·오래된 재시도 차단입니다. 네이티브 SecureStore·Android 설치·FCM 수신·화면 꺼짐과 실제 탑승은 별도 검증입니다.

독립 리뷰에서 재생 응답에 없는 전송 상태를 “전송 없음”으로 보일 수 있는 표현을 확인해, 상태를 조회하기 전에는 “조회 필요”로 표시하도록 보완했습니다.
